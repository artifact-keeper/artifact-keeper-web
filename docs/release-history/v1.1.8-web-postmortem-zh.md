# 事后复盘：v1.1.8 web 镜像从未发布

**问题：** https://github.com/artifact-keeper/artifact-keeper-web/issues/320
**撰写日期：** 2026-05-04
**状态：** 已解决（已记录，未回填）

## 摘要

`ghcr.io/artifact-keeper/artifact-keeper-web:1.1.8` 不存在。后端 v1.1.8 的 Helm chart 引用了该镜像，因此 v1.1.8 chart 的全新安装会在 web 组件上以 `ImagePullBackOff` 失败。

## 根因

后端仓库（`artifact-keeper`）与 web 仓库（`artifact-keeper-web`）作为独立的 Git 仓库发布，各自拥有自己的标签历史与 Docker 发布工作流。后端仓库中的 Helm chart 默认将 `backend.tag` 与 `web.tag` 都固定为相同的值，其假设是两个仓库会打出匹配的版本标签。

这个假设被打破了。`artifact-keeper-web` 的版本标签历史如下：

| 标签                | 提交 SHA     | 标签类型    | 创建日期（creatordate）   |
| ------------------- | ------------ | ----------- | ------------------------- |
| v1.1.0-rc.1 至 rc.9 | （各不相同） | （混合）    | 2026-02 至 04             |
| v1.1.1              | f7b32f61     | lightweight | 2026-04-19 14:42:52 -0500 |
| v1.1.0              | f7b32f61     | annotated   | 2026-04-19 14:46:10 -0500 |
| v1.1.2              | 8b10b104     | lightweight | 2026-04-20 17:36:25 -0500 |
| v1.1.3              | 304cb71a     | lightweight | 2026-04-20 17:56:24 -0500 |

（注意：按创建日期 v1.1.1 排在 v1.1.0 之前 —— 两者指向同一个 SHA。v1.1.1 要么是错误产生的重复，要么是刻意的重新打标签，其过时的 lightweight 标签在四分钟后的 annotated v1.1.0 创建后从未被清理。意图已无法还原。无论哪种情况，v1.1.2 与 v1.1.3 也都是 lightweight 标签，这意味着从 v1.1.1 起 web 仓库没有签署的发布边界 —— 这是此处不处理的另一个卫生问题。）

本仓库**没有 `v1.1.4`、`v1.1.5`、…… `v1.1.8` 或 `v1.1.9` 标签**。`package.json` 目前为 `1.1.3`。web 发布流程实际上止步于 v1.1.3，而后端继续到 v1.1.4、v1.1.5、v1.1.6、v1.1.7、v1.1.8（现在还有 v1.1.9）。**v1.1.4 至 v1.1.7 的 web 标签被接受为永久缺口** —— 也没有计划回填其中任何一个。（如果某个 CVE 迫使 v1.1.9 发布前需要 v1.1.x 补丁，请从 `release/1.1.x` 上的 v1.1.3 SHA 打 v1.1.4 —— v1.1.3 之上的缺口是可保留的，而非已污染。下面的"不回填"决定专门针对 v1.1.8，因为*后端*已经在该标签下发布了。）

`gh run list --workflow docker-publish.yml --limit 50` 从工作流侧确认了同样的图景：没有任何由 `v1.1.8` 标签推送触发的运行，因为这样的标签根本不存在。发布工作流并非"v1.1.8 未运行"—— 它从未被邀请运行。

v1.1.8 的 chart Helm values 仍固定 `web.tag: 1.1.8`，因为那是 chart 的默认约定。拉取该镜像会得到 404，因此在 #320 中报告了 `ImagePullBackOff`。

## 为什么会发生

- 没有任何发布列车自动化强制 web 仓库为每个后端标签打标签。两个仓库独立漂移。
- Helm chart 没有防御性默认值，例如 `web.tag: latest` 或回退到最新的可用 web 版本。
- 发布工作流中没有镜像发布门禁，无法在发布时捕获"已固定但缺失"的镜像。该门禁在 `artifact-keeper#882` 中跟踪。

## 决策

**不要回填 `ghcr.io/.../artifact-keeper-web:1.1.8`。**

理由：

1. 本仓库没有可供构建的 `v1.1.8` 源引用。最接近的"本应成为 v1.1.8"的是 `v1.1.3`（提交 `304cb71a22921855217e8612f2b5a813eeae22ca`），但从 `v1.1.3` 源引用合成 `:1.1.8` 标签会制造一个永久的出处谎言：镜像标签、attestation 与 SBOM 都会指向 v1.1.3，而标签却声称是 v1.1.8。
2. 后端 v1.1.8 chart 已在用户手中，任何回填镜像都不会匹配该 chart 构建时所依据的完整性预期。
3. 修复是向前的，而非向后的：发布下一个稳定的 web 标签，并将 chart 重新固定到它。

**考虑过并拒绝的替代方案：**

- _`:1.1.8` 上的墓碑 manifest_ —— 发布一个立即报错并给出清晰"此标签从未发布"消息的 manifest。已拒绝：Docker 注册表没有"故意损坏"标签的原语；我们发布的任何 manifest 都会被拉取，用户看到的是运行时错误而不是 `ImagePullBackOff`。当前的 404 实际上比伪造的墓碑是更清晰的信号。
- _指向 v1.1.3 构建的浮动 `:1.1.8-mitigation` 标签_ —— 与回填相同的出处异议，外加关于哪个标签是规范的额外混淆。
- _chart 侧热修复，在 v1.1.8.1 chart 中重新固定 `web.tag = 1.1.3`_ —— 这位于后端仓库的 chart 代码中，不在此处。在 `artifact-keeper#886`（v1.1.9 发布跟踪）中单独跟踪，下一个 chart 将在那里固定真正的 v1.1.9 web 镜像。

**已采取的行动：**

- 将 v1.1.8 web 记录为永久不可恢复（本文件）。
- 在变更日志中注明 v1.1.8 web 从未发布。
- 下一个 web 稳定标签应为 `v1.1.9`，从 #331 引入的新 `release/1.1.x` 分支打出（首选 —— 保持 v1.1.x 维护与 `main` 的漂移分离）。v1.1.9 chart 随后将固定真正的 `web:1.1.9` 镜像。

## 受影响运维人员的临时解决方案

如果全新安装或升级落在了 v1.1.8 chart 上，并且你在 web 组件上遇到 `ImagePullBackOff`：

```sh
# 在 v1.1.9 发布前，将 web 镜像显式固定到最后一个已知良好的 v1.1.x web 标签
helm upgrade <release> <chart> --reuse-values \
  --set web.image.tag=1.1.3
```

注意事项：

- v1.1.3 web 不包含后端 v1.1.4 至 v1.1.8 中落地的变更。如果 chart 的 web/backend 配对假设功能对等（例如 SDK 契约变更），UI 可能表现异常。据我们所知，v1.1.4-v1.1.8 的后端变更没有任何一项破坏前端 API 表面，因此实际上这应该只是外观层面的问题。
- 浮动 `:dev` 标签（跟踪 `main`）以及一旦打出后的 `:1.1-dev` 标签（本 PR —— 跟踪 `release/1.1.x`）是替代方案，但它们刻意是**可变的** —— 不适合生产环境固定。它们的存在是为了发布门禁，而不是面向最终用户的安装。

当 v1.1.9 发布时，切回 `--set web.image.tag=1.1.9`（或移除覆盖并消费 chart 默认值）。

## 预防

更长期的门禁是 `artifact-keeper#882` —— 一个发布时检查，若 chart 引用的任何镜像在注册表上不可解析则发布失败。该工作不在本 PR 范围内，但它是防止复发正确的位置。

`artifact-keeper-web#331`（本 PR）中的配套变更新增了 `release/1.1.x` 分支与 `:1.1-dev` 浮动标签，因此 v1.1.x 发布门禁可以不再依赖 `:dev` 标签（它随 `main` 浮动），而是针对真正的 v1.1.x web 镜像进行测试。**`:1.1-dev` 是一个可变浮动标签**，仅供发布门禁使用。它不适合 chart 固定或用户安装；chart 应固定特定的 `:1.1.x` semver 标签。

运维说明：`release/1.1.x` 分支应在任何推送之前，以分支保护（要求 PR + 评审 + 状态检查）创建，因为对该分支的推送会覆盖 `:1.1-dev`。与 `main` 上现有 `:dev` 标签相同的信任模型适用。
